A wallet's answer that arrives after the site's lock was lost (an IndexedDB lease that lapsed while the user was in the wallet) is kept, not dropped.

- `keepOutcome(locks, write, later?, settled?)` (review entry): `write()` now; refused for a lost lock, the outcome is kept and applied once the work under `locks` ended, under the same handles taken back. This holds for every lock `browserLocks`/`fencedLocks` hands out, whatever the backend (native Web Locks, the IndexedDB lease, the in-tab queue). Kept outcomes take the lock afresh one at a time: when the work ends, every kept outcome is queued for the lock in the order it was kept before any runs, and one kept later (or after any of `locks` ended) is queued at once behind them, never written ahead. Without `later`, `write` runs again only if no other tab took the locks since (each acquisition stamps the lock's last holder). With `later`, which matches the attempt by its identity and merges into the latest record, it lands whenever the locks are free, keeping another tab's unrelated update. Otherwise the record stays as the lost lock left it. `settled(applied)` is told once whether a kept outcome was applied in the end.
- `sendReviewed`, `resumeReviewed` and `completeReviewedStep` keep `onUnsent` (a 4001 after the lapse ends the site's attempt instead of leaving it "sending"), and an `onSubmitted`/`onConfirmed` refused for the lost lock. `payRelayrReviewed` keeps `onSent`, the sped-up mined hash included, and gains `onUnsent` for a definite unsent after `onSending` began (a 4001, or the adapter's fence refusing before the wallet); the caller gets the wallet's error. `attemptScoped: true` on either opts the site's callbacks into the identity-matched mode. Safe Relayr's `fund()` uses the same mechanism.
- `LockLostError` shows `LOCK_LOST_LINE` through `errorLine` (its message stays for logs). `REVIEW_STOPPED_LINE` is the shared line for a stopped run.
- `useReviewedRun` follows only a write its run reserved, one this runner followed before (its own, though its calls changed), its saved sequence's, or the exact same call: a form refused by another form's write on a shared hold ends with the hold's line and adopts nothing, and a retry of the action whose write it still follows is refused without replacing that follow (read live, so a "Try again" that resets and runs from one render's handle follows it again). A later run under the same hold (its intent's, though the calls were refreshed) from the same account, whose form's earlier single-call write succeeded, closes as done on it and sends nothing, even if another reader acknowledged that success: matched by reservation through the action's last step's hold (a Safe batch's MultiSend proposal included, as the run follows it), whatever steps now precede it (a refreshed approval), never by call bytes, never by an earlier step's success, and checked before preparing, after preparing and at the final send gate.
- A last step `dismiss` closed while it was followed (an EOA send or a Safe proposal) stays observed: a run of the same calls is refused with the hold's line while it confirms, and closes as done on its success (acknowledged once shown) instead of sending again. Different calls, or a later run, send.
- `keepOutcome` is exported from the review entry.
- `onConfirmed` delivery is one state on the hold's claim: delivered, pending (kept for a lost lock, or another completion's claim not yet told) or undelivered (given back). Every step ends the same way in `sendReviewed`, `resumeReviewed` and `completeReviewedStep`: its notice told, and only once delivered is the step recorded done in its sequence's journal, so an earlier step's undelivered notice is told by the next resume before any later step is sent. A success is acknowledged or shown done only once its notice was delivered: `sendReviewed` and `resumeReviewed` end at the receipt (`ReviewedReceiptUnverifiedError`) instead of done, and `completeReviewedStep` returns `undelivered: true`, while it is pending or undelivered. The handle gains `settleConfirmed(settled, delivered)` and `confirmation(settled)`; a pending claim left by a closed tab is claimable again after 5 minutes. `useReviewedRun` keeps such a step pending and unacknowledged, keeps following it, and a later run of the form (its own write remembered across dismiss) closes on it only after telling `onConfirmed` under that run's own locks.
- Each sent step's outcome is saved on its hold with its reservation before the wallet opens: the account, the step, the call as it was sent, the earlier steps' hashes and the run's signatures, kept as long as the call's last 8 settlements. Every recovered result and callback is built from it, never from a later run's calls or the journal: `completeReviewedStep` (scoped or not; its result gains `hashes`, the action's hashes through that step, and `signatures`), `resumeReviewed` (its done now carries the first run's signatures, which the sequence's journal saves), the run itself, and `useReviewedRun`'s own-success close and `ended()`. A retry under the same intent with refreshed calldata tells `onConfirmed` the call that was sent; a reopened signed action is done with its signatures; an unscoped sequence's completion is done with every step's hash. `WriteHoldGate.beforeSend` takes the encoded outcome and the handle gains `outcomeOf(reservation)`. `useReviewedRun` holds a run that closes on its own success open, and keeps the form's own write, until that done has rendered: a dismiss meanwhile is refused, and a reopen closes on it again instead of sending.
- A receipt's `ended()` never waits on a notice queued behind work its own locks still run (kept for a lock the run lost, or another completion's claim waiting for one, whoever owns it): it ends `failed` with `ConfirmationQueuedError` (`CONFIRMATION_QUEUED_LINE`, retryable, nothing sent again), so a site may await it inside its lock's scope; `onConfirmed` is told once that work ends (or by the form's next run), and only then is the success acknowledged and shown done.
- `useReviewedRun` keeps the form's ownership of each write per sending account and reservation, so one payment's dismissal or shown done never clears another's, and a reopen of either closes on its own success instead of sending again. Each entry only moves forward (owned, then shown; a dismissing run once listed is never dropped), through one merge every writer uses, and is keyed by the account that sent it, never the one connected when the user dismisses or a continuation runs: a run reads its account once, so switching accounts and back never lets a retry pay twice.
- `attachHash` returns `hashCheck`: `"attached"`, `"mismatch"` (read, and another transaction) or `"unverified"` (any read failure, retryable). `HELD_HASH_MISMATCH_LINE` and `HELD_HASH_UNVERIFIED_LINE` are the shared lines.
- `lapsingLocksForTests()` (`testing`): a lock manager whose lease can be made to lapse, to install as `navigator.locks` in a site's tests.
